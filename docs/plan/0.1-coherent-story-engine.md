## 1. Problem Statement

NexusRPG currently has the right ingredients for a local-first AI RPG—FastAPI, Next.js, Ollama, LanceDB, Axiom, and Chronos—but the central product promise is not yet proven. A player must be able to make consequential choices and trust that characters, inventory, relationships, world rules, quests, and past events remain coherent after many turns, a restart, and a branch.

This milestone establishes the first compelling proof of concept for Plotline: one playable adventure whose exact facts survive the full lifecycle. It creates the foundation for eventually transforming a finished story into an editable comic, voiced video, or other media, while explicitly deferring those expensive outputs until the underlying story is worth adapting.

## 2. Goals

- Prove a complete local adventure loop of approximately 20–30 turns.
- Persist exact canonical world state separately from generated scene prose.
- Make restart and branch behavior deterministic, isolated, and testable.
- Make the critical user journey fast enough to feel responsive on CPU-only hardware with 16 GB RAM.
- Establish outcome-based QA that tests what a player can accomplish and observe, not merely whether selectors or endpoints respond.
- Build security boundaries before importing user lore, exposing files, or adding sharing.
- Preserve a clear path to Plotline: durable story events and structured state must be exportable to future comic, voice, and video pipelines.

## 3. Non-Goals

- Comic, webtoon, storyboard, image, voice, or video generation in this milestone.
- Payments, hosted multiplayer, public sharing, accounts, or production SaaS infrastructure.
- Cloud LLMs, hosted vector databases, or paid APIs.
- A fully autonomous AI that may freely mutate canonical facts.
- A large content library, procedural universe generator, or unrestricted real-time AI simulation.
- Replacing Chronos before tests demonstrate a concrete limitation.
- Optimizing for benchmark latency at the expense of correctness, debuggability, or user-visible quality.

## 4. Personas & User Stories

- **As a player**, I want the game to remember what I did and what I possess so that choices feel meaningful.
- **As a returning player**, I want to close and reopen an adventure without losing the story or its consequences.
- **As a branching player**, I want to explore an alternate choice without corrupting my original timeline.
- **As an author/player**, I want characters, locations, rules, relationships, and lore to remain distinguishable from scene prose.
- **As a future Plotline creator**, I want a chronicle containing structured events, characters, relationships, and assets so that a completed story can later become a comic or voiced video.
- **As the maintainer**, I want tests to reproduce failures with the exact request, state, model configuration, and commit lineage.
- **As a local user**, I want the application to work without sending story data to a cloud service.

## 5. Functional Requirements

- **FR-1.** The system MUST support a named adventure/campaign boundary; state from one campaign MUST NOT appear in another.
- **FR-2.** The system MUST store canonical state as structured data, including at minimum characters, locations, items and holders, relationships, quests, rules, active scene, and known facts.
- **FR-3.** Generated prose MUST NOT be the sole source of truth for canonical facts.
- **FR-4.** Every accepted turn MUST record a parent commit, scene/event record, resulting canonical state or deterministic state transition, and enough metadata to reconstruct the turn.
- **FR-5.** A choice that changes a canonical fact MUST pass through a deterministic, validated transition boundary before the state is committed.
- **FR-6.** The system MUST reconstruct any reachable commit exactly, including after a fresh engine/process restart.
- **FR-7.** The system MUST support creating a branch from an earlier commit without copying or mutating the source branch’s later state.
- **FR-8.** Branches MUST preserve shared history up to their fork point and MUST isolate all later canonical changes and scene history.
- **FR-9.** The actor/generation path MUST receive state reconstructed from the requested parent commit, not an unrelated global current state.
- **FR-10.** Lore retrieval MUST identify whether a returned fact came from authored lore, canonical state, or prior event history.
- **FR-11.** The system MUST validate generated or requested state changes against Axiom rules before they become canonical.
- **FR-12.** The system MUST provide a recoverable error when a model is unavailable, times out, emits invalid structured output, or proposes an invalid state change.
- **FR-13.** The player MUST be able to resume the last committed scene and see the committed story feed for the selected campaign/branch.
- **FR-14.** The proof-of-concept MUST pass the acceptance scenario: roughly 24 turns, restart, factual memory checks, and one divergent branch.
- **FR-15.** Future adaptation data MUST be represented as stable story events and entity references rather than requiring reverse-engineering from prose.

## 6. Non-Functional Requirements

- **Performance** — Keep API/state operations local and non-blocking. Target p95 under 250 ms for state reconstruction, commit, branch, and retrieval excluding LLM generation; target first streamed scene token under 8 seconds on the reference CPU setup after model warm-up. Bound history/lore retrieval by top-k and token budgets. Do not run multiple CPU-heavy model generations concurrently by default.
- **Security** — Bind local services to the minimum needed interfaces; do not expose Ollama, Chronos files, LanceDB files, or raw host paths through browser-controlled parameters. Validate and canonicalize all filesystem paths. Use allowlisted model names, request-size limits, timeouts, subprocess restrictions, safe JSON parsing, and parameterized persistence operations. Treat imported lore and model output as untrusted data. Never commit secrets or `.env`.
- **Privacy & Compliance** — The proof of concept is local-first and must clearly disclose that imported text/images are processed locally. Do not add telemetry or external uploads without explicit opt-in. Hosted privacy/compliance claims are deferred.
- **Accessibility** — New UI MUST preserve keyboard navigation, visible focus, readable contrast, semantic controls, loading/error announcements, and reduced-motion support; target WCAG 2.1 AA for added UI.
- **Scalability** — Use campaign-scoped records and stable identifiers so a future SQLite canonical store can replace a fragile shared JSON file without changing story semantics. Keep Chronos objects content-addressed/immutable where possible.
- **Reliability** — Commits MUST be atomic or recoverable after interruption. Replaying the same deterministic transition against the same parent MUST be idempotent or rejected as a duplicate. A failed generation MUST NOT advance the branch.
- **Observability** — Log correlation ID, campaign ID, branch, parent/child commit IDs, transition ID, model name, latency, token counts where available, retrieval counts, validation result, and error category. Do not log full private lore or secrets by default.
- **Maintainability** — Keep canonical state, event history, Chronos persistence, retrieval, model orchestration, and HTTP/UI adapters in separate modules. Add tests before broad UI work. Mark documentation as current, proposed, or deferred.
- **Internationalization** — Keep user-facing strings externalizable; no hard-coded locale assumptions in timestamps or future export metadata.
- **Backward compatibility** — Preserve existing Chronos object formats and behavior unless a migration is tested. If state schema changes, version it and provide explicit migration or a clear incompatible-version error.

## 7. Acceptance Criteria

- **AC-1.** *Given* a fresh local data directory, *when* a user creates one scripted adventure with an item, an NPC secret, a relationship, a quest, and a rule, *then* the adventure has a campaign ID, a root commit, and an initial branch.
- **AC-2.** *Given* a valid campaign, *when* approximately 24 turns are committed, *then* every turn has a parent, event/scene record, validated resulting state, and reconstructable commit.
- **AC-3.** *Given* the 24-turn adventure, *when* a fresh Chronos/state engine is opened against the same storage, *then* the selected branch reconstructs the same canonical state and committed scene feed.
- **AC-4.** *Given* a choice that transfers an item, reveals or withholds an NPC secret, and changes a quest, *when* the resulting commit is reconstructed, *then* item holder, NPC knowledge, relationship/knowledge state, and quest status match exact expected values.
- **AC-5.** *Given* an earlier commit, *when* a new branch is created and a different choice is committed, *then* the branch contains its own changed facts while the original branch retains its original facts.
- **AC-6.** *Given* prose that contradicts canonical state, *when* the next scene is generated, *then* canonical state and validation win; the contradiction is recorded as an error/repair signal rather than silently becoming fact.
- **AC-7.** *Given* an invalid transition, oversized request, invalid branch/commit identifier, path traversal attempt, model timeout, or malformed model output, *when* the request is made, *then* the system rejects it safely, does not advance the branch, and returns a useful bounded error.
- **AC-8.** *Given* a second campaign, *when* it is played after the first, *then* no characters, items, lore, events, or commits from the first campaign are retrieved or displayed.
- **AC-9.** *Given* a normal player journey, *when* the player resumes, chooses, branches, and returns to the original branch, *then* the visible result matches the selected branch and no stale client-only feed is required.
- **AC-10.** *Given* the reference CPU-only environment, *when* state operations and bounded retrieval are measured over a representative fixture, *then* they meet the p95 targets in section 6 and produce no unbounded memory growth.
- **AC-11.** *Given* a pull request containing a story-flow change, *when* the QA workflow runs, *then* automated tests produce artifacts on failure and a reviewer verifies the customer outcome with an exploratory checklist.

## 8. Data Model

Proposed canonical boundaries:

- `campaigns`: id, name, schema_version, created_at, updated_at, active_branch.
- `branches`: campaign_id, branch_id, name, fork_commit_id, tip_commit_id, created_at.
- `commits`: campaign_id, branch_id, commit_id, parent_commit_id, scene_event_id, state_hash, model_metadata, created_at.
- `world_states`: campaign_id, commit_id, canonical JSON/state snapshot or Chronos reference.
- `story_events`: campaign_id, branch_id, commit_id, event type, structured payload, visible prose reference, actor/source, created_at.
- `lore_documents`: campaign_id, document_id, source metadata, content hash, ingestion status.
- `entity_records` and `relationship_records`: stable IDs, typed fields, provenance, validity interval/commit range where needed.

Initial implementation MAY use Chronos plus versioned files if that is the least risky path. Move canonical campaign metadata to SQLite when the current shared `world_state.json` cannot safely express multiple campaigns or atomic updates. Every table/index MUST be campaign-scoped. Enforce uniqueness on campaign/branch/commit identifiers and foreign-key relationships. Avoid storing secrets or raw private content in logs.

## 9. API Surface

Existing routes MUST be inspected and preserved where compatible. The target contract is:

- `POST /campaigns` — create campaign; local-only access.
- `GET /campaigns` — list campaigns.
- `GET /campaigns/{campaign_id}` — campaign summary and selected branch.
- `POST /campaigns/{campaign_id}/branches` — fork from a validated commit.
- `GET /campaigns/{campaign_id}/branches/{branch_id}/timeline` — committed events/scenes.
- `POST /actor/scene` — generate/stream the next scene from campaign, branch, and parent commit.
- `POST /actor/choose` — validate choice, apply deterministic transition, commit event/state, and return the new commit.
- `GET /campaigns/{campaign_id}/state?commit_id=...` — reconstruct exact canonical state.
- `POST /import/text` and future image import routes — campaign-scoped, size-limited, asynchronous where needed.
- `GET /health` — health only; no sensitive configuration.

Requests MUST use typed IDs and bounded JSON bodies. Responses MUST include campaign/branch/commit IDs, provenance for factual data, and a stable error shape. Streaming MUST have heartbeat/timeout behavior and MUST NOT commit a turn until the transition succeeds. OpenAPI schemas MUST be updated with examples for success, validation failure, restart, and branch isolation.

## 10. UI / UX

Preserve the existing Map, Play, and Timeline visual identity and expand the smallest flow necessary:

1. Create or select a campaign.
2. Start/resume the main branch.
3. Read a streamed scene and make a choice.
4. See a clear committed/resolving/error state.
5. Open the timeline and branch from an earlier commit.
6. Switch branches and verify the visible history/state changes.
7. Reopen the app and resume without relying on React-only memory.

The UI MUST show loading, model unavailable, invalid response, empty campaign, stale branch, and retry states. Branch changes MUST require clear labeling. The UI MUST NOT expose raw file paths, internal prompts, hidden system instructions, or secrets. Use semantic buttons/links, keyboard-accessible timeline controls, focus management after streaming/error states, and mobile-friendly layouts.

## 11. AI / ML Considerations

- Use Ollama locally with an allowlisted configured model; keep model choice separate from canonical state.
- Treat the model as a narrator/planner that proposes scene prose and structured transition intent, not as the authority over facts.
- Use a bounded prompt assembled from current canonical state, relevant authored lore, relevant prior events, active goals, and explicit rules.
- Require structured output for transition intent; validate against a schema, Axiom rules, entity IDs, and allowed operations.
- Provide a deterministic fallback fixture/script for acceptance tests so core correctness does not depend on nondeterministic generation.
- Measure factual consistency, invalid-transition rate, latency, and recovery behavior. Do not use prose quality as a substitute for state correctness.
- Redact or avoid PII in model prompts where possible. Never send local data to a remote model in this proof of concept.
- Future adaptation should consume the event/entity chronicle, not scrape arbitrary generated prose.

## 12. Integration Points

- **Chronos** — commit objects, snapshots/deltas, refs, reconstruction, fork, checkout, pruning; preserve existing behavior and extend only behind tests.
- **Axiom** — deterministic validation of state transitions and world rules.
- **LanceDB** — bounded retrieval for authored lore and indexed event history, with campaign/location filters.
- **Ollama** — local scene generation, embeddings, and optional image import model; timeouts and model availability handling required.
- **FastAPI** — request validation, streaming, error contracts, and campaign scoping.
- **Next.js/Tailwind/React Flow** — play, map, timeline, and branch selection.
- **Docker Compose** — reproducible local services, health checks, resource-conscious defaults.
- **Future Plotline exporters** — structured chronicle, character sheets, scene boundaries, visual descriptions, dialogue, and provenance. These are interfaces to design now, not implementation scope for 0.1.

## 14. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Model prose contradicts facts | H | H | Canonical state + typed transitions + Axiom validation; prose never becomes fact automatically |
| Shared JSON state corrupts or mixes campaigns | H | H | Campaign scope, atomic writes, schema versioning, then SQLite canonical records |
| Branch mutates main timeline | M | H | Immutable commits, isolated refs, branch-isolation acceptance test |
| CPU generation feels too slow | H | M | Stream output, warm model, bounded context/retrieval, one generation at a time, smaller configurable model |
| Retrieval returns stale or wrong-world lore | M | H | Campaign/location filters, provenance, deterministic fixtures, retrieval tests |
| AI agents make conflicting edits | M | H | One code owner, small PRs, source-of-truth docs, independent review |
| Tests pass while player experience fails | M | H | Outcome-based Playwright journeys, exploratory QA, failure video/log artifacts, customer-risk prioritization |
| Security regression through imports or paths | M | H | Abuse-case tests, strict IDs/paths, size/time limits, no raw host path exposure |
| Scope expands into media too early | H | M | Media interfaces only; gate comic/video work on story acceptance criteria |
| Tests become flaky or slow | M | M | Deterministic fixture mode, isolated temp storage, stable accessibility selectors, retries only for diagnosis—not to declare correctness |

## 15. Rollout Plan

- **Feature flag name & default state:** `NEXUS_CANONICAL_STORY_LOOP`; disabled until API and UI acceptance suites pass. The direct Chronos test may run independently.
- **Migration sequencing:** document current schema → add versioned campaign/state contracts → add compatibility reader → migrate fixtures/data → enable deterministic transition path → remove unsafe global-state writes only after regression coverage.
- **Dogfood / pilot cohort:** the owner and a small local test group using Docker Compose on Ubuntu/WSL2, CPU-only, 16 GB RAM. Use a scripted test adventure before personal long-form campaigns.
- **GA criteria:** AC-1 through AC-11 pass; no known branch-isolation or campaign-leak defect; security abuse checks pass; performance targets pass on the reference machine; at least one manually completed adventure remains coherent after restart and branching.
- **Rollback path:** keep old Chronos objects readable, preserve a backup of local data, gate new transition routes, and provide a clear read-only recovery mode. Never silently rewrite or delete story history.

## 16. Test Plan

- **Unit** — state schema validation; deterministic transitions; Axiom rules; ID/path validation; event provenance; Chronos commit serialization, reconstruction, refs, fork, and pruning.
- **Integration** — FastAPI routes with temporary campaign storage; scene-from-parent reconstruction; choice-to-commit flow; restart; model timeout/malformed output; no branch advancement on failure; campaign isolation.
- **End-to-end** — Playwright tests the customer outcome: create campaign, play turns, reload browser, resume, branch from an earlier point, switch branches, and confirm visible facts/history. Prefer accessible roles and user-visible outcomes over brittle CSS selectors.
- **Security** — authorization/scoping matrix for every campaign/branch/commit route; path traversal; invalid IDs; oversized payloads; malformed JSON; prompt/content injection from lore; model-output injection; denial-of-service limits; secret/log review; exposed-port review; dependency audit.
- **Accessibility** — automated axe checks on changed pages plus keyboard-only play/timeline/branch flows and manual screen-reader spot checks.
- **Performance / load** — benchmark reconstruction, commit, fork, retrieval, and first-token latency with 24-, 100-, and 500-turn fixtures; track p50/p95, memory, disk growth, and CPU saturation. Use a single local Ollama generation for the reference path.
- **Manual exploratory** — test as a customer with a written mission: create an adventure, make meaningful choices, intentionally contradict the narrator, restart, branch, lose/reconnect Ollama, submit invalid input, and verify recovery. Record exact steps, expected outcome, actual outcome, logs, screenshots/video, commit IDs, and severity.
- **QA operating approach** — adopt the linked poteto approach as an outcome-first, high-feedback loop: keep the critical journey executable, make failures observable and reproducible, use automation for repeatable coverage, and require human review of whether the product actually worked. A green test is not accepted when it only proves a selector clicked or an endpoint returned 200.
- **Change gate** — every story-state change adds or updates a deterministic test; every UI flow change updates an outcome-based E2E test or explicitly documents why it is not needed; every failure is classified as product bug, test bug, environment issue, or flaky test before retrying.

## 18. Open Questions

2. What exact canonical state schema best represents knowledge, relationship changes, inventory, quest state, and provenance without overfitting one story?
3. Should a branch be identified by a human name, immutable ID, or both?
4. What is the minimum Ollama model that meets acceptable factual consistency and first-token latency on the 16 GB CPU reference machine?
5. Which event types are required for the first Plotline chronicle export: dialogue, action, discovery, relationship change, item transfer, quest transition, location change, and rule violation?
6. How should a player manually correct an incorrect canonical fact while preserving an audit trail?
